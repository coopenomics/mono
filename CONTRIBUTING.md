# Contributing

Спасибо за интерес к проекту. Этот документ описывает, как мы принимаем изменения в монорепозитории «Цифровой Кооператив».

## Принципы

1. **Основная ветка разработки — `dev`.** Вся работа ведётся относительно неё.
2. **Любая фича идёт через Pull Request в `dev`.** От `dev` создаётся дочерняя ветка, в неё коммитится работа, затем открывается PR обратно в `dev`.
3. **Зонтичный PR.** Одна фича — один PR (или один зонтичный PR на эпик). Вливаем, когда фича готова и проверена целиком, а не кусками «на потом».
4. **Прямые коммиты в `dev`** допустимы только для хотфиксов. Ветка сейчас не защищена от прямых пушей, но принцип тот же: фичи и обычные изменения — через отдельные ветки и PR.
5. После merge в `dev` изменения попадают в следующие релизы (нарезка на окружения — отдельный релизный процесс, здесь его не описываем).

## Как сделать изменение

```bash
# 1. Актуализировать базовую ветку
git checkout dev
git pull origin dev

# 2. Создать дочернюю ветку
git checkout -b feat/short-description
# или: fix/..., chore/...

# 3. Внесите изменения, закоммитьте

# 4. Запушьте ветку и откройте PR в `dev`
git push -u origin HEAD
```

В описании PR кратко укажите:

- что сделано и зачем;
- как проверить (ручной чеклист, если уместно);
- связанные issue / тикеты, если есть.

Ревьюер смотрит на готовность фичи целиком. Если PR ещё не готов к merge — пометьте его как draft.

## Требования к качеству кода

Перед открытием PR (и до merge) изменения должны проходить проверки сборки. Иначе CI / сборка упадут и PR не примут.

- **Линтер** — без ошибок ESLint (и аналогов в затронутых пакетах).
- **TypeScript** — без ошибок типов. Для PR в `dev` CI гоняет typecheck по ключевым пакетам (`desktop`, `controller` и зависимости workspace).
- **Сборка затронутых пакетов** — если меняли библиотеку (`cooptypes`, `sdk`, `factory`, …), убедитесь, что она собирается и потребители не ломаются по типам.

Локально (примеры):

```bash
# Typecheck / lint в конкретном пакете
pnpm --filter @coopenomics/controller run typecheck
pnpm --filter @coopenomics/desktop run lint

# Или точечная проверка типов без полной сборки приложения
pnpm --filter @coopenomics/controller exec tsc --noEmit
```

Не коммитьте код, который заведомо ломает линтер или типы.

## Стиль и соглашения

- **Менеджер пакетов — pnpm.** Установка зависимостей только через фильтр компонента из корня:

  ```bash
  pnpm add <пакет> --filter @coopenomics/controller
  ```

  Не ставьте пакеты глобально в корень «на глаз» и не используйте npm/yarn для workspace-пакетов.

- **Имена веток** — понятные префиксы: `feat/…`, `fix/…`, `chore/…`, при необходимости с номером задачи.
- **Коммиты** — строго по формату ниже. Без id задачи историю потом не связать с трекером.
- Следуйте сложившимся паттернам в том слое, который меняете:
  - backend (`components/controller`) — NestJS, чистая архитектура;
  - frontend (`components/desktop`) — Vue 3 + Quasar, Feature-Sliced Design;
  - контракты (`components/contracts`) — C++ / EOSIO.

Подробности по конкретному компоненту — в его `README.md` / `AGENTS.md` рядом с кодом. Этот гайд не дублирует архитектурную документацию.

## Формат коммитов (обязательно)

Каждый коммит должен быть привязан к задаче. Без символов идентификации в начале сообщения мы не сможем сопоставить коммит с задачей в трекере. Для написания текстов коммитов рекомендуем использовать ИИ (создать персональный скилл по шаблону ниже). 

Шаблон:

```text
[<id>][@<username>] <тип>: <действие> — <зачем это нужно>
```

| Часть | Что писать |
|-------|------------|
| `<id>` | Номер задачи из трекера задач на платформе (или уточните у мастера) |
| `<username>` | Ваш логин / ник в проекте |
| `<тип>` | Один из: `feat`, `fix`, `refactor`, `docs`, `config` |
| `<действие>` | Кратко, что сделано |
| `<зачем>` | Зачем это нужно (бизнес-причина или техническая необходимость) |

Правила:

- Тип обязателен.
- После тире (`—`) обязательно указать **зачем**.
- В сумме сообщение — не короче ~10 слов (тип + действие + зачем).
- Не копируйте дифф в сообщение. Не пишите голое «исправлено» / «обновлено» без пояснения.

Примеры:

```text
[562-32][@ant] docs: добавить CONTRIBUTING с правилами PR в dev — чтобы контрибьюторы сразу знали ветки и формат коммитов
[123][@ivan] feat(desktop): кнопка паузы таймера на задаче — чтобы можно было прервать учёт времени без остановки сессии
```

Запрещено:

```text
[123] Исправлено
fix: правки
wip
```

## Что не нужно делать

- Не пушить крупные фичи напрямую в `dev` в обход PR.
- Не открывать десяток мелких PR на одну и ту же незавершённую фичу, если достаточно одного зонтичного.
- Не оставлять в PR заведомо красный линтер / typecheck «потому что потом поправим».
- Не коммитить без `[id][@username]` и без части «— зачем».
- Не коммитить секреты (`.env`, ключи, токены).

## Быстрый старт окружения

Установка, Docker и скрипты разработки описаны в корневом [README.md](./README.md). Для вклада достаточно уметь поднять нужный слой и прогнать проверки качества из раздела выше.

## Вопросы

Если неочевидно, куда класть изменение или как оформить PR — спросите в обсуждении к issue / в черновике PR до большого объёма работы.
