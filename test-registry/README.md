# Реестр тестов

Отвечает на вопрос «что у нас проверено по фиче, а что нет» — по всем трём
уровням сразу: контракт, бэкенд, UI.

Один файл на фичу, имя файла совпадает с полем `feature`.

```
test-registry/
  capital.result-submission.yaml
  registration.onboarding.yaml
```

Почему плоский каталог, а не рядом с кодом: фича по определению пересекает три
уровня и несколько компонентов, и колокация заставила бы выбирать ей дом.
Плоский каталог делает вопрос «что есть / чего нет» одним `glob`.

## Схема

```yaml
feature: capital.result-submission     # <домен>.<фича>, строчными; = имя файла
title: Подача результата и акт-2

# Где живёт фича. Гейт по этим маскам связывает изменённый файл с фичей,
# поэтому маски должны реально покрывать её код. Любой уровень может отсутствовать.
sources:
  contract:
    - components/contracts/cpp/capital/p.cap.rid.standard.yaml
  backend:
    - components/controller/src/extensions/capital/application/use-cases/result-*.ts
  ui:
    - components/desktop/extensions/capital/features/Result/**

cases:
  - id: cap.rid.happy.01               # уникален по всему реестру
    level: backend                     # contract | backend | ui
    kind: happy                        # happy | side | break
    scenario: Пайщик подаёт результат по проекту с активным заданием
    expect: создан result, эмиттится o.cap.accept
    test: components/controller/tests/unit/capital/result-submission.test.ts
    status: passing                    # missing | written | passing

  - id: cap.rid.side.07
    level: backend
    kind: side
    scenario: Повторная подача того же результата (двойной клик)
    expect: conflict, второй submit не создаёт запись
    test: ~
    status: missing
    decision_needed: true              # поведение не выводится из кода — нужен ответ человека
```

### Значения полей

| поле | смысл |
|---|---|
| `level` | `contract` — стандарт процесса и цепь; `backend` — controller; `ui` — desktop |
| `kind` | `happy` — основная ветка; `side` — боковая (права, статусы, повторы, пустые данные); `break` — намеренная поломка (сервис лёг, токен истёк, гонка) |
| `status` | `missing` — случай выявлен, теста нет; `written` — тест есть; `passing` — тест есть и зелёный |
| `decision_needed` | поведение нельзя вывести из кода и оно не описано в стандарте — нужен ответ человека, иначе тест зафиксирует текущий баг как норму |

`status: missing` обязан идти с пустым `test`, и наоборот: любой статус выше
требует существующего файла теста — иначе отчётность врёт.

## Команды

| команда | что делает |
|---|---|
| `pnpm registry:audit` | карта покрытия: по фичам — случаи и статусы; отдельно области кода, не заведённые в реестр |
| `pnpm check:registry` | гейт: схема валидна, пути к тестам существуют, у тронутых зарегистрированных фич реестр обновлён |
| `pnpm mutate:changed` | проверка добросовестности тестов мутациями по изменённым файлам |

## Границы метода

Реестр защищает от забывчивости, а не от халтуры. Тест, написанный
«чтобы позеленело», пройдёт и гейт, и валидацию. Единственная механическая
защита от этого — мутационное тестирование: если после порчи исходника тест
остаётся зелёным, он ничего не проверяет.

Поэтому `status: passing` без прогона мутаций означает лишь «тест существует и
не падает», а не «поведение защищено».
