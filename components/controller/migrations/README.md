# Миграции

В контроллере две ленты миграций с разными задачами.

## Схема базы — миграции TypeORM

Таблицы, колонки, индексы и ключи меняют **только миграции** (C28-79).
`synchronize` выключен везде: он молча удалял колонку, которой нет в сущности,
превращал переименование в «удалить + добавить» и в blue-green выкатке правил
общую базу, пока старая версия ещё работала.

- Ядро держит миграции в `src/infrastructure/database/migrations/` (список —
  `index.ts`), расширение — в своём каталоге `migrations/database/` и объявляет
  их в записи реестра (`databaseMigrations`, файл `<имя>.database-migrations.ts`).
  Вынесенное расширение уносит историю своих таблиц с собой.
- Учёт — таблица `schema_migrations`. Порядок — метка времени в имени класса,
  одна лента для ядра и расширений.
- Применяются при подключении приложения (`migrationsRun`), первым шагом
  `pnpm migrate` и командой `pnpm schema:migrate` (её зовёт перезапуск стенда
  до boot).

Правка сущности → миграция:

```bash
pnpm schema:generate add_member_since   # SQL выписывает TypeORM, файл регистрируется сам
pnpm schema:check                        # пустая база + все миграции = сущности (гейт CI)
pnpm schema:check --database voskhod     # только чтение: чем живая база отличается от кода
```

Правка схемы сущности (декоратор или опция колонки) без новой миграции того же
владельца роняет `pnpm check`: гейт `check-schema-migrations` сверяет дифф ветки от
общей с dev точки. Правка, которая таблицу не меняет, помечается в самой правке
комментарием `// schema-unchanged: причина`.

Сгенерированный SQL — черновик: переименование колонки TypeORM выписывает как
удаление и добавление, такую миграцию переписать на `RENAME COLUMN`; новая
`NOT NULL`-колонка в заполненной таблице требует умолчания или двух шагов.

Стартовые миграции (`*-baseline.ts`) идемпотентны: на пустой базе создают всё, на
базе, которую раньше вёл `synchronize`, только дотягивают недостающее. Их
сгенерировал `pnpm schema:baseline`; повторно он не нужен.

Известное расхождение старых баз, намеренно не исправляемое. У колонки `status`,
которую сущности наследуют из `BaseTypeormEntity` (кошельки и соглашения пайщика,
комментарии, голоса и состояние Благороста, решения КУ и др.), значение по
умолчанию годами «утекало» от соседних сущностей через ошибку TypeORM (теперь
исправлена патчем). Часть наследников пишет строку без статуса и опирается на это
значение, поэтому старые базы сохраняют своё (`registered`, `pending`…), а новые
получают `UNDEFINED`. `schema:check --database` показывает это как
`SET DEFAULT 'UNDEFINED'` — безвредно.

## Данные и цепь — мигратор контроллера

Этот каталог — миграции данных: перенос и досчёт строк, действия в цепи.
Запускаются `pnpm migrate` после миграций схемы.

- Новые файлы: `ГГГГММДДччмм__описание.ts` (UTC, `pnpm migration:generate <имя>`).
  Ключ учёта — метка: его не нужно вычислять от предыдущего файла, и две ветки
  не получат один номер.
- Прежние `V{версия}__описание.ts` заморожены: они применены на узлах под своими
  версиями, переименование заставило бы мигратор прогнать их заново. Идут
  первыми, по версии; новые — после, по метке.
- Тестовые миграции (`__test` в имени) запускаются всегда.
- `validUntil` (дата) — миграция не применяется после этой даты (UTC).
