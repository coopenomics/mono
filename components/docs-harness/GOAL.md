# Цель работы: один артефакт вместо трёх

Свести документацию, визуальные тесты и реестр тестов **в один артефакт** —
сценарий `docs-harness`. Из одного прогона сценария выходит:

1. **вердикт теста** — прошёл/упал, с причиной;
2. **кадры** — PNG для документации либо для визуального контроля;
3. **запись в реестре** — `test-registry/marketplace.*.yaml`, статус проставляется
   механически по вердикту, а не руками.

Пока это три отдельных процесса, они расходятся: скриншоты протухают, реестр
врёт, а тесты живут отдельно от того, что видит пользователь.

## Что должно получиться

- Все **39 marketplace-сценариев** зелёные под одной командой
  `pnpm test:ui:marketplace`.
- Сюита **вне релизного гейта CI**: не входит в `pnpm test` / `test:unit` /
  `test:ci`, не вызывается через `workflow_call` из `release.yaml`.
  Запуск — только явной командой либо `workflow_dispatch`.
- Маркетплейс заведён в реестр как область (сегодня — крупнейшая непокрытая:
  388 файлов `controller/src/extensions/marketplace`, 29 файлов
  `contracts/cpp/marketplace`, 288 файлов UI в `desktop/src/**/Marketplace*`).
- Прямой путь закрыт UI-случаями; боковые ветви перечислены от кода;
  верхние из них закрыты backend-тестами.

## Критерий готовности

- Сюита зелёная от `reboot:extra` до конца цепочки состояния.
- `pnpm registry:audit` показывает marketplace среди заведённых фич.
- В отчёте — **отдельными списками**: настоящие дефекты продукта и случаи
  `decision_needed` (поведение не выводится из кода — нужен ответ человека).

## Механика (как именно сводится в один артефакт)

Сценарий — единственный источник. Связь с реестром через `meta`:

```js
export const meta = {
  title: 'Оформление заказа',
  feature: 'marketplace.order-create',   // файл в test-registry/
  cases: ['mkt.order.happy.01'],         // какие случаи закрывает
  mode: 'docs',                          // docs | shots | test
  docPath: 'new/marketplace/orderer/order-create.md',
  assetsDir: 'assets/new/marketplace/orderer/order-create',
  role: 'user',
  fixtures: ['petrova'],
};
```

`meta` целиком уезжает в `manifest.json` (`writeManifest(mod.meta)`), поэтому
новые поля доезжают до реестра без отдельного механизма.

### Три режима

| `mode` | кадры | проза | install в docs | зачем |
|---|---|---|---|---|
| `docs` | да | да | да | страница инструкции (nav в mkdocs уже заведён) |
| `shots` | да | нет | нет | визуальный след: экран не развалился, смотрится глазами |
| `test` | только `FAIL.png` | нет | нет | боковые: отказ по правам, чужой акт, выдача без кода |

### Вердикт

`run.mjs` пишет `shots/<scenario>/result.json` — `{status, at, feature, cases,
reason}`. Сценарий роняется не только ассертом, но и **JS-ошибкой на странице
или 4xx/5xx от GraphQL** — этого достаточно, чтобы 39 сценариев стали смоук-
тестами без единой дописанной строчки. Прицельные `opts.expect` (статус, сумма,
число строк, наличие кнопки) добавляются сверху по мере восстановления.

### Синхронизация реестра

`bin/registry-sync.mjs` читает манифесты и вердикты и проставляет в
`test-registry/marketplace.*.yaml`:

- `test:` — путь к `.mjs` сценария;
- `status:` — `passing` только если сценарий зелёный в последнем прогоне,
  `written` если тест есть, но красный или протух.

Тогда `passing` честен без ручной бухгалтерии.

## Порядок работы

- **Ф0** — механика: `mode`/`feature`/`cases`, вердикт, `registry-sync.mjs`,
  `run-marketplace-all.mjs` (группы + `reboot:extra`), команда,
  узкие корни маркетплейса в `SIGNIFICANT_ROOTS`.
- **Ф1** — восстановление по цепочке состояния (иначе никак, сценарии
  необратимо двигают цепь): onboarding → chairman → offerer/предложение →
  orderer/заказ → отгрузка → приёмка → маркировка → выдача → возврат →
  списание → board.
- **Ф2** — `test-registry/marketplace.<слайс>.yaml` по слайсам.
- **Ф3** — backend-тесты на верхние боковые, точечно `jest -i`.
- **Ф4** — `mutate:changed` строго по тронутым файлам.

## Правила, которые не нарушать

- Расхождение текста/селектора — чиню в сценарии. Настоящий дефект продукта —
  чиню только если тривиален и однозначен, иначе в отчёт.
- Полный `jest` / `vue-tsc` локально не запускать — вешает сервер.
- Коммит → сразу пуш, после каждого доведённого сценария.
- Не подгонять тест под текущее поведение: если должное поведение не выводится
  из кода — `decision_needed: true`, а не «зафиксируем как есть».

## Ограничение: мутации на этом стенде не запускаются

`pnpm mutate:changed` падает на инициальном прогоне: Stryker перед мутациями
обязан один раз прогнать весь набор тестов controller'а, и это не укладывается
в его таймаут (5 минут), а на живом dev-стенде такой прогон ещё и вешает
машину — ровно то, что запрещает CLAUDE.md.

Это ограничение инфраструктуры, а не выполненный шаг: без мутаций статус
`passing` в реестре означает «тест есть и зелёный», но не «поведение
защищено». Место для мутаций — CI, где стенд одноразовый и полный прогон
допустим.

Что проверено вместо этого: каждый связанный с реестром тест прогнан точечно
(`jest -i <файл>`) и был зелёным на момент простановки статуса.

### Семь дефектов подготовки, из-за которых `--reboot` был неработоспособен

1. **Фикстуры не создавались вовсе.** `fixturesOfScenario` искала в исходнике
   литеральный путь `state/participants/<имя>.json`, а сценарии строят его
   через переменную и объявляют состав в `meta.fixtures` — который сюита не
   передавала. Набор всегда выходил пустым.
2. **`add-plain-participant` не подписывал соглашение ЦПП «Кошелёк».** Пайщик
   заводился, но `ledger2::walletop` отбивал любое движение средств.
3. **L3-гейт заказчика двусоставной** — `requires_gate || !cart.delivery_braname`.
   Одной подписи оферты мало: её могли поставить на регистрации, где выбора
   участка не было. Отсюда фаза `05-sign-offer` — подпись **и** участок.
4. **`reboot` не сбрасывал `state/gate-used.json`** — на чистой цепи пул
   пайщиков для гейта считался израсходованным.
5. **Preflight не ждал контроллер** — после reboot coopback ещё компилируется,
   и прогон падал «подними стек» сразу после успешного reboot.
6. **Страница онбординга живёт только до подписи оферты**: после неё грант
   `Onboarding:orderer` не выдаётся, маршрут исчезает. Сценарий L2 обязан брать
   свежего пайщика из пула, а не рабочую фикстуру.
7. **Сценарии разошлись с интерфейсом**: исчезнувшая колонка суммы, хардкод
   суммы заказа, `:visible` на портал-контейнере с нулевыми метриками.

### Дефект продукта

`putImage` пропускал **пустой файл изображения** — проверялся только MIME.
sha256 от нуля байт валиден, объект уезжал в bucket, карточка предложения
получала неотображаемую картинку, заменить нечем: ключ content-addressed.
Добавлена проверка длины до записи.

### Про мутации — уточнение к разделу выше

Stryker на стенде по-прежнему не запускается, но статус `passing` теперь
означает больше, чем «тест зелёный»: каждый тест этой ночи проверен **ручной
мутацией** — правится проверяемое место, тест обязан покраснеть, код
возвращается. Это трижды вскрыло собственные тесты-пустышки:

- проверка суммы заказа била в валидацию цены, а мутация порога схлопывания
  выживала (добавлен случай 0.0001 ₽/кг × 0.001 кг);
- regex отказа цепи допускал «Повторите подписание» — фразу содержит и
  соседняя ошибка «не получен tx_hash»;
- локатор пустого списка заказов совпадал с названием таба «Получены».

**Мутация, которая не компилируется, ничего не проверяет**: jest отдаёт
«0 tests» вместо красного, и это легко принять за успех.

### Ловушка прогона: точечный ≠ в цепочке

`--only` для сценария из середины цепочки обманчив. Сценарий выдачи без кода
проходил точечно и падал в сюите: на столе оставался оверлей предыдущего шага,
кнопка находилась, но клик не проходил. Новый сценарий обязан быть проверен
прогоном в цепочке (`--from=<он>`), а не только точечно.

### Что осталось незакрытым

- `return` и `writeoff` (15 случаев) — вынесены заказчиком в отдельную работу.
- `mkt.cat.side.07` — глобальная уникальность имени категории: ждёт решения
  (запрет или переиспользование; рекомендация — переиспользование через
  существующую `available_categories`).
- Оставшиеся UI-случаи требуют либо второго председателя КУ с привязкой к

## Итог ночи 2026-08-09/10 (ветка `feat/marketplace-tests-n2`, база `dev`)

Цель захода: закрыть шесть оставшихся основных сценариев (установка расширения,

### Ключ ко всей ветке возврата: гарантийный срок

Гарантийный срок возврата задаётся ровно в одном месте — в диалоге одобрения
предложения председателем, где поле предзаполнено нулём. Срок снимается в заказ
при оформлении (`warranty_period_secs`) и на выдаче замерзает как
`warranty_until = now + secs`. **Задним числом его не поднять.**

Прежние прогоны одобряли предложение с нулём. Отсюда недостижимой была не
только подача заявления на возврат, но и списание: обезличенный остаток на
складе участка появляется именно из принятого возврата
(`restockReturnedItem`), а без него список кандидатов на списание пуст. Одна
правка — 30 дней при одобрении — открывает обе ветки сразу.

### Три дефекта подготовки, из-за которых стенд не поднимался

1. **MinIO брал дефолтный порт.** В `.env` сдвинуты все host-порты, кроме
   MinIO: он вставал на 9000, занятый соседним чекаутом, и не стартовал.
   `extra_reboot.sh` ждёт его через `docker compose exec minio` — то есть висел
   бы вечно. Добавлен сдвиг по общей формуле (9040/9041).
2. **`docker compose down` сносил фронт.** Подкоманда список сервисов не
   принимает и удаляет ВСЕ контейнеры проекта. Фронт терялся дважды: reboot его
   обратно не поднимал (прогон падал на преflight'е уже после успешной
   перезагрузки), а поднятый заново `quasar dev` компилирует маршруты с нуля —
   кэш трансформаций живёт в памяти процесса, на диск не ложится. Холодный
   фронт не успевал отдать страницу за таймауты: витрина приходила пустой, а
   оформление заказа оставалось спиннером. Теперь сносим ровно перечисленные
   сервисы через `rm -svf`, именованные тома удаляем явно, фронт не трогаем.
3. **Сидинг ПВЗ молча пропускался.** Ожидание таблицы `marketplace_ku_details`
   было две минуты, а контроллер поднимается через ts-node и на загруженной
   машине компилируется дольше. Без ПВЗ select пунктов выдачи приходит пустым.
   Порог поднят до десяти минут, там же выровнен преflight раннера.

### Оба сценария L1 были пустышками

`install-market` и `coop-accept-cpp` целиком состояли из `if (count())` и
`.catch(() => {})` — они проходили и при неустановленном расширении. Добавлены
проверки конечного состояния.

### Приём ЦПП не может быть UI-случаем

Фазы подготовки раннер выполняет один раз до всех сценариев, а `01-l1-accept`
принимает ЦПП решением совета: без этого у председателя нет ни одного
admin-права расширения и все экраны отдают «Недостаточно прав доступа». К
моменту открытия экрана ЦПП уже принята, и кнопки «Принять» там нет в принципе.
Случай переведён на backend, где он уже покрыт (`accept → status=active`);
экран остаётся документированным сценарием без привязки к случаю.

Тем же порядком переведены ещё два случая: нулевой гарантийный срок (на стенде
он теперь ненулевой, в одном прогоне обоих состояний не бывает) и двойное
одобрение предложения (после первого одобрения предложение уходит из очереди,
повторно нажать нечем; защита — `requirePending`, уже покрыта).

### Дефект продукта: состав проекта списания не проверяется

`validateAndNormalizeItems` проверяет только заполненность полей (участок,
наименование, сумма, причина) и принимает любые `inventory_ids`. Ни
`createDraft`, ни `submitToCouncil`, ни `confirmWriteoff` не сверяют, что
позиции — обезличенный остаток кооператива на складе, а не имущество, уже
выданное пайщику. На исполнении `applyStatusTransition(invId, 'WRITTEN_OFF')` —
безусловный UPDATE без сверки исходного статуса. Единственная защита — фильтр
`findWriteoffCandidates` в списке кандидатов, то есть подсказка интерфейса, а
не правило сервера. Записан в реестр, не чинился: место проверки (черновик /
подача в совет / подтверждение складом) — проектное решение.

### Что мешает прогонам на этом стенде

Машину делят соседние чекауты: load average держится 14–20 при шести ядрах.
Компиляция контроллера занимает около десяти минут, фронт компилирует маршруты
на лету. Любая параллельная нагрузка ломает прогон — собственный запуск
точечного jest во время boot'а уронил загрузку цепи с
`tx_cpu_usage_exceeded`. Во время прогона на машине не должно идти ничего
своего.

### Про мутации — ещё два способа обмануться

Все новые тесты проверены ручной мутацией, и по дороге вскрылись два способа
получить ложное «покрыто»:

1. **Мутация, которая не компилируется, ничего не проверяет** — jest отдаёт
   «0 tests» вместо красного. Поймано дважды: `false && …` перед проверкой и
   инверсия `=== null` там, где TypeScript сужает тип и следующая строка
   перестаёт компилироваться. В таких местах мутируем то, что компилируется:
   текст отказа или границу сравнения.
2. **Мутация может попасть не в тот метод.** `if (!proposal.is_pending_confirmation)`
   встречается в файле дважды; правка первой попавшейся строки прошла мимо
   проверяемого места и **выжила молча**. Проверять надо не только «покраснело
   ли», но и куда именно легла правка.

### Следующий шаг для списания, независимый от контракта

Обезличенный остаток на складе участка появляется из двух источников: принятый
возврат (сейчас недоступен) и **недовыдача** — когда оператор выдаёт меньше
принятого. Второй путь контракт не задевает. Если сценарий выдачи научить
отпускать часть позиции, склад получит остаток, и обе истории списания
поедут — заодно закроется `mkt.iss.side.04`. Требует полного прогона от
чистой цепи: суммы заказа изменятся.
