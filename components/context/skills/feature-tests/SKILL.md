# Покрытие фичи тестами через реестр

Цель — не «написать тесты», а получить обоснованную уверенность, что изменение
кода не сломает поведение молча. Тесты, которые не падают при поломке, этой
цели не служат и хуже отсутствия тестов: они создают ложное спокойствие.

## Инварианты, которые нельзя нарушать

**Не подгонять тест под текущее поведение.** Если из кода нельзя понять, как
поведение *должно* работать, — это не повод зафиксировать как есть. Такой тест
превратит баг в норму и будет защищать его от исправления. Помечай случай
`decision_needed: true` и выноси человеку списком.

**Не считать фичу покрытой, пока не прогнаны мутации.** `status: passing`
означает лишь «тест есть и зелёный». Добросовестность проверяет только
`pnpm mutate:changed`: выживший мутант = тест ничего не проверяет.

**Не заводить случаи, которых не бывает.** Реестр, набитый умозрительными
сценариями, обесценивается. Каждый случай должен быть достижим из UI, API или
цепи — иначе его не заводить.

**Не редактировать чужие случаи при слиянии.** Новые дописываются, существующие
сохраняются вместе со статусами.

## Фазы

### 1. Локализация

Найди код фичи. Работает и когда фичи нет в документации:

- бэкенд — `components/controller/src/extensions/<домен>/` и `src/domain/<домен>/`;
- UI — `components/desktop/extensions/<домен>/`;
- контракт — `components/contracts/cpp/<домен>/*.standard.yaml` и `.cpp`.

Зафиксируй маски в `sources` будущего файла реестра так, чтобы они реально
покрывали код фичи: по ним гейт связывает изменённый файл с фичей.

### 2. Источники истины

Собери то, что описывает *должное* поведение, в порядке убывания авторитета:

1. `.standard.yaml` процесса — канон для уровня контракта;
2. PRD и архитектура в `~/blago/production/<проект>/_bmad-output/`;
3. код — описывает только фактическое поведение, не должное.

Если первых двух нет, это нормально: переход к фазе 3 не блокируется. Но тогда
любой спорный случай уходит в `decision_needed`.

### 3. Перечисление ветвей

Механический обход, не наитие. Метод — как в скилле
`bmad-review-edge-case-hunter`: пройти все ветвления и границы, выписать
**только необработанные**, без оценок «хорошо/плохо».

Обязательные классы для этого проекта:

- **права**: не пайщик, не председатель, не член совета, чужой кооператив;
- **статусы**: операция в неподходящем статусе процесса, повтор терминального перехода;
- **повторы и гонки**: двойной клик, две подписи одновременно, повторный вебхук;
- **данные**: пусто, ноль, отрицательное, превышение, дробные остатки;
- **связность**: сущность удалена, ссылка висит, документ не подписан;
- **инфраструктура** (`kind: break`): БД недоступна, цепь не отвечает, токен истёк, ABI устарел после деплоя.

Каждая найденная ветвь становится случаем с `kind: side` либо `break`.

### 4. Слияние в реестр

Файл `test-registry/<домен>.<фича>.yaml` по схеме из `test-registry/README.md`.
Новые случаи — со `status: missing` и пустым `test`. Затем `pnpm check:registry`
должен быть зелёным (схема, пути, обновление реестра при тронутом коде).

### 5. Тесты по уровням

- **contract** — сценарий стандарта: порядок статусов, права, инварианты цепи.
- **backend** — `components/controller/tests/unit/<домен>/`, jest, `-i`.
  Отдельно API-проба: те же сценарии, но напрямую по ручкам — интерфейс мог
  скрыть кнопку, а сервер обязан отказать самостоятельно.
- **ui** — сценарий `components/docs-harness/scenarios/<домен>/`, Playwright
  через интерфейс, без обращения к API проекта.

После каждого написанного теста — обнови `status` и `test` в реестре.

### 6. Проверка добросовестности

`pnpm mutate:changed` по затронутым исходникам. Выживший мутант означает, что
тест не проверяет поведение: доработай тест, а не отключай мутатор. Только
после этого `status: passing` честен.

### 7. Отчёт

Коротко: сколько случаев заведено, сколько закрыто на каком уровне, какие
мутанты выжили и почему, и — отдельным списком — что требует решения человека
(`decision_needed`). Этот список не растворять в прозе: он и есть то, что
дальше блокирует покрытие.

## Команды

| команда | назначение |
|---|---|
| `pnpm registry:audit` | карта покрытия и области кода вне реестра |
| `pnpm check:registry` | гейт реестра |
| `pnpm mutate:changed` | мутации по изменённым файлам |
| `pnpm --filter @coopenomics/controller run test` | юнит-тесты бэкенда |

## Чего не делать

Не отдавать перечисление ветвей и написание тестов пачке фоновых агентов:
пользователь этого не хочет, и качество падает. Скилл — про твою собственную
работу по шагам.

Не расширять `SIGNIFICANT_ROOTS` в `scripts/lib/registry.mjs`, чтобы «покрытие
выглядело лучше». Это подделка отчётности.
