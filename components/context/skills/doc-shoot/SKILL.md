# doc-shoot

Автоматизация создания и обновления документации через Playwright-сценарии. Пользователь говорит «сделай мне инструкцию на логин» — ты прогоняешь orchestrator, дописываешь прозу по фактам со скриншотов, показываешь результат.

## Как работает

Harness живёт в `<repo>/components/docs-harness/` (workspace-пакет `@coopenomics/docs-harness`, private). Один сценарий = один `.mjs` в `scenarios/<раздел>/<имя>.mjs`. Сценарий ходит по UI и вызывает `shot(page, name, description)`; harness пишет `shots/<раздел>/<имя>/*.png` + `manifest.json`.

MD-черновик собирается из `manifest.json` через `lib/render-md.mjs`. Финальное расположение в репозитории docs — через `lib/install.mjs` (копирует PNG в `docs/assets/...` и MD в `docs/new/...`).

Путь docs-репо по умолчанию — соседняя `../components/docs/docs/` относительно harness (у каждого разработчика своя клонированная папка; никогда не писать в чужой клон). Явно переопределить можно через `--docs-root=<path>` на install.mjs.

## Главный вход — `bin/shoot.mjs`

Один скрипт, который делает весь pre-flight и прогон без ручной возни:

```bash
cd docs-harness && node bin/shoot.mjs <scenario>            # обычный прогон
cd docs-harness && node bin/shoot.mjs <scenario> --reboot   # с предварительной полной перезагрузкой стека
```

Что он делает по шагам (и почему):

0. **`--reboot` (опционально)** — `pnpm run reboot:extra` перед всем остальным: сносит `blockchain-data` и volumes, пересоздаёт цепочку и БД, делает `boot:extra` (председатель + полный совет), запускает parser и controller заново. Удаляет все фикстуры в `components/docs-harness/state/participants/*.json` (их WIF невалидны после новой цепочки) — на следующем шаге пересоздадутся. Используй когда сценарий нужен «с нуля» или цепочка/БД разъехались с состоянием.
1. **Стек** — проверяет chain/controller/parser. Если что-то лежит — `docker compose up -d <service>` и ждёт до 60-120с. Если после этого всё равно не отвечает — fail с пояснением.
2. **dist** — `components/cooptypes/dist/index.mjs` и `components/sdk/dist/index.mjs`. Если их нет (свежий клон / `git clean`), desktop отдаёт пустой спиннер и все скриншоты будут пустыми. Orchestrator билдит через `pnpm --filter ... build`.
3. **desktop dev** — `:2999`. Если не запущен — поднимает в фоне (`pnpm run dev` в `components/desktop`), ждёт до 180с. Если был запущен И только что собрали dist — рестартует, потому что `vite-plugin-checker` держит кэш «no module» и vue-tsc overlay перехватывает клики Playwright.
4. **Фикстура** — парсит сценарий регэкспом на `state/participants/<name>.json`. Если файла нет, лезет в `KNOWN_FIXTURES` (внутри `bin/shoot.mjs`) за профилем (email + ФИО) и создаёт через `add-plain-participant.ts`, пишет JSON в state. Незнакомый username → fail с подсказкой добавить профиль в реестр.
5. **Прогон** — `node run.mjs <scenario>`. Если упал — указывает на `FAIL.png` и `console.log`.
6. **draft.md** — если черновика ещё нет, генерит скелет через `render-md.mjs`. Существующий не трогает.

Что НЕ делает (намеренно):
- Не пишет прозу в `draft.md` — это работа Claude по фактам со скриншотов.
- Не запускает `install.mjs` — запись в `components/docs/docs/` происходит руками после ревью прозы.

## Когда дёргать `--reboot`

Триггер-фразы пользователя «сделай ещё раз», «с нуля», «перезагрузи всё», «обнули», «полный перезапуск» — обычно означают `--reboot`. Также делай reboot самостоятельно если:

- сценарий падает на чём-то типа «account already exists» / «duplicate key» — старая цепочка не совпадает с фикстурой
- фикстура пайщика есть в файле, но логин не проходит — WIF в state не валиден на текущей цепочке
- между прогонами накопилось состояние, которое мешает чистому сценарию (например, тестовые транзакции, документы, голосования)

Reboot занимает ~3-5 минут (большая часть — `boot:extra` с компиляцией контрактов и регистрацией совета). После него **все** фикстуры пайщиков нужно создавать заново — orchestrator делает это сам на шаге 4.

В этом репо (`/home/admin/mono-ai-1/`) у тебя есть явное разрешение на `pnpm run reboot:extra` и `docker compose` команды — не спрашивай разрешения каждый раз. См. memory `feedback_infra_permissions.md`.

## Фиксированные конвенции

- **Размер скриншота.** Все сценарии используют viewport **1120×800 CSS-пикселей при deviceScaleFactor = 1.25** → PNG выходит 1400×1000 пикселей с UI, отрисованным крупно и читаемо. Параметры зашиты в `lib/harness.mjs` (константы `SHOT_VIEWPORT` и `SHOT_SCALE`) — менять их не надо, иначе в документации поедут размеры.
- **Имена тестовых пайщиков.** Только человеческие: `ivanpetrov` / Иван Сергеевич Петров, `ekaterina` / Екатерина и т.д. **Никаких `testpay1`, `tester`, `userN`** — они идут в скриншоты и выглядят плохо. Фикстуры кэшируются в `components/docs-harness/state/participants/<username>.json` и переиспользуются между прогонами.
- **`components/desktop/.env` живёт на локальном бэкенде.** `BACKEND_URL=http://127.0.0.1:2998`, `CHAIN_URL=http://127.0.0.1:8888`, `CHAIN_ID=<локальный>`. Файл в `.gitignore`, так что локальные правки в PR не утекут. **Не возвращай его на dev.coopenomics.world** между сценариями — следующий прогон тут же сломается; это часть постоянного dev-окружения на сервере.
- **Проза в `draft.md` не генерится автоматом.** `lib/render-md.mjs` создаёт скелет только если файла нет (или с `--force`). Повторный прогон сценария НЕ перезатирает написанный тобой текст. Пиши полноценную прозу с admonitions (`!!!warning/note/info/danger`) — именно этот draft.md `install.mjs` кладёт в `new/<раздел>/<имя>.md` как финальный документ.

## Обязательные шаги при создании **нового раздела** документации

Если meta.docPath сценария указывает на файл в папке, которой раньше в `components/docs/docs/new/` не было:

1. Создать папку `new/<раздел>/` (директория для MD-файла).
2. Создать папку `assets/new/<раздел>/<имя>/` (директория для PNG; путь должен совпадать с `meta.assetsDir` сценария, nested-структура).
3. **Обновить `components/docs/mkdocs.yml`** — добавить новую секцию в `nav:`. Без этого страница не попадёт в меню и навигацию сайта. Смотри существующие секции (`Регистрация пайщика`, `Стол пайщика`) как образец.

Все три шага делаются **до** install.mjs; пропустишь mkdocs.yml — страница не попадёт в сборку документации, хотя файл будет существовать.

## Фактологическая дисциплина

- Пиши прозу **строго по тому, что видно** на скриншотах. Если нужна деталь, которой нет на кадре (текст ошибки, callback при невалидных данных, заголовок модалки) — иди в репу и ищи факт там (Grep по Vue/TS-компонентам). **Никогда не предполагай** поведение UI из общих соображений.
- Если факт собрать не удалось — либо добавь отдельный сценарий, который этот факт снимет, либо пропусти описание; плохая инструкция — та, которая врёт пользователю.

## Создание нового пайщика для скриншотов

Для сценариев, где нужен «чистый» свежий пайщик с собственным ключом (не председатель, не член совета, не shared chairman key):

```bash
MONGO_URI=mongodb://127.0.0.1:27017/cooperative-x \
  pnpm --filter @coopenomics/boot exec esno \
  src/scripts/add-plain-participant.ts \
  <username> <email> <firstName> <lastName> [middleName]
```

Скрипт:
- Идемпотентен: при повторном запуске проверяет `registrator::get_account`; если username уже есть ончейн, не пересоздаёт (но и WIF возвращает `null` — сохранять его должен harness при **первом** создании).
- Делает полную цепочку: keypair → `registrator::adduser` → `registrator::changekey` → mongo `individual` → pg `users` (role=user, status=active, is_registered=true).
- Вывод — JSON в stdout: `{username, email, wif, publicKey, coopname}`. Сохраняй wif в `components/docs-harness/state/participants/<username>.json` при создании.

!!!note "Онбординг соглашений"
    Свежесозданный пайщик при первом входе попадает на обязательное подписание 4 соглашений (пользовательское соглашение, ЭП, политика конфиденциальности, ЦПП Кошелёк) — это нормальный UX, а не баг. Для инструкций, не связанных с первым входом, сценарий должен программно подписать все соглашения, иначе не доберётесь до «нормального» экрана.

## Параллельные сессии пайщиков

Нативно через Playwright: `browser.newContext()` создаёт полностью изолированные сессии (свои cookies/localStorage/storageState) в одном процессе. Для сценариев, где нужно одновременно видеть действия нескольких пайщиков (собрания, голосование, обсуждение в проекте):

```js
const [ctx1, ctx2] = await Promise.all([browser.newContext(), browser.newContext()]);
await loginAs(ctx1, participant1);
await loginAs(ctx2, participant2);
// скриншоты с каждой стороны — как два разных человека за разными компьютерами
```

Для ускорения повторных прогонов — один раз залогиниться, сохранить `context.storageState()` в JSON, переиспользовать через `browser.newContext({ storageState: '...' })`.

## Алгоритм под запрос пользователя

1. **Определи намерение**. Варианты:
   - «пересними скриншоты к существующей инструкции X» — сценарий уже есть, `bin/shoot.mjs <scenario>` обновит PNG
   - «сделай новую инструкцию на X» — сценария нет, сначала создать `.mjs`, потом `bin/shoot.mjs`
   - «покажи что сломалось в UI на шаге X» — прогнать, смотреть `FAIL.png` и `console.log`

2. **Запусти orchestrator** — он сам сделает pre-flight стека, билды dist, рестарт desktop, создание фикстуры. Если сервисы лежат — поднимает через `docker compose up -d`:
   ```bash
   cd docs-harness && node bin/shoot.mjs <scenario>            # обычный
   cd docs-harness && node bin/shoot.mjs <scenario> --reboot   # с полным reboot:extra
   ```

3. **Новый сценарий — процесс**:
   - Спроси пользователя что именно документируем (роль, начальное состояние, ключевые шаги)
   - Если есть существующий MD — найди через `grep -rl "X" components/docs/docs/` (относительно текущего клона!) и возьми оттуда шаги как основу
   - Напиши файл `scenarios/<раздел>/<имя>.mjs` по образцу `scenarios/auth/signin.mjs`. Обязательно: `meta.title`, `meta.docPath`, `meta.assetsDir`, `meta.role`
   - Если нужен новый тестовый пайщик с именем, которого нет в `KNOWN_FIXTURES` (`components/docs-harness/bin/shoot.mjs`) — добавь туда профиль (email + ФИО), иначе orchestrator зафейлится на шаге фикстуры
   - Запусти `node bin/shoot.mjs <раздел>/<имя>`
   - Если упало — покажи FAIL.png, не продолжай

4. **Обновление существующего**:
   - `node bin/shoot.mjs <раздел>/<имя>` — пересоздаст PNG, старые перезапишутся; `draft.md` не трогается
   - `node lib/install.mjs <раздел>/<имя>` — скопирует PNG в docs. MD по умолчанию не трогается (PNG обновились — прошлая проза актуальна).
   - `node lib/install.mjs <раздел>/<имя> --md` — принудительно перекладывает `draft.md` поверх `docs/new/<раздел>/<имя>.md`. Используй когда правил прозу в shots/draft.md и хочешь её в docs.

5. **Написание прозы в MD** — твоя работа, не скрипта:
   - Прочти `draft.md`, посмотри каждый скриншот через `Read`
   - Для каждого шага добавь 2–4 предложения: что пользователь видит, что должен сделать, на что обратить внимание
   - Сохраняй alt-тексты (они уже осмысленные из description)
   - Не изобретай UI-элементы, которых не видно на скриншоте
   - Сохраняй MD обратно в `shots/<scenario>/draft.md`, потом пользователь решает — копировать ли в `components/docs/docs/` через `install.mjs --md`

## Типовой флоу ответа

Не захламляй вывод — пользователь хочет готовый черновик, не лог каждой команды.

```
Подготавливаю сценарий <name>... [если нужно]
Прогоняю... [run.mjs]
✓ 5 скриншотов сняты
Черновик MD: <path>
Картинки: <path>
Дальше: проверь визуально, потом install.mjs — скопирую в docs.
```

Если создавал сценарий с нуля — предупреди: «этот сценарий теперь есть, каждый следующий прогон обновит картинки».

## Гейты

- НЕ запускай сценарии на удалённом dev.coopenomics.world — только локальный стенд.
- НЕ коммить в mono-ai-2 автоматически. install.mjs просто копирует файлы; пользователь сам делает commit/push.
- Если сценарий падает из-за флапающего UI (таймауты, race conditions) — пофикси селекторы/ожидания в сценарии, не добавляй `sleep`-ы вслепую.
- Если meta.docPath уже существует в mono-ai-2 и пользователь хочет обновить прозу — diff'ни существующее против draft, не затирай чужую работу.
