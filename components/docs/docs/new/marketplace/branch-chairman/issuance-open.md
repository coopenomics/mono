# Открытие выдачи заказов на ПВЗ

Раздел `/<coopname>/market-pvz/issuance` (Story 6.6) — рабочее место
**председателя кооперативного участка** (он же оператор ПВЗ в access-matrix
расширения). Здесь оператор открывает выдачу заказов пайщикам — первой
подписью signiss1 включает заказ в ленту «Готово к получению», а после
прихода пайщика собирает финальную подпись `signiss2`.

Доступ — `roles: ['chairman']` в workspace `market-pvz`.

## Как открыть ленту

Над таблицей — два элемента:

- **Поле «ID кооперативного участка в…»** — председатель вписывает
  идентификатор КУ, чьи выдачи хочет видеть. У председателя кооператива
  может быть несколько КУ под рукой; чтобы не показывать «общую кашу»,
  лента грузится только после явного выбора участка.
- **Кнопка «Загрузить ленту выдач»** (primary, зелёная) — стартует
  GraphQL-запрос `marketplaceListIssuanceQueue(branchId=…)` и
  показывает заказы этого КУ.

!!!info "Почему именно так"
    Лента ограничена access-matrix marketplace правилом
    `Order: ['read:own-KU']` (оператор видит только свой ПВЗ). Поле
    «ID КУ» нужно для явности — председатель кооператива технически
    может быть operator'ом на нескольких ПВЗ; UI просит выбрать,
    куда сейчас «зашёл», а не угадывает по контексту.

## Таблица ленты выдач

После загрузки таблица показывает заказы по столбцам:

| Колонка       | Что в ней                                                                   |
|---------------|-----------------------------------------------------------------------------|
| **Заказ**     | Идентификатор заказа.                                                        |
| **Заказчик**  | Имя пайщика (полное ФИО или username для контроля выдачи).                   |
| **Количество**| Сумма позиций.                                                               |
| **Сумма**     | Стоимость заказа.                                                            |
| **Статус**    | `ACCEPTED_TO_COOP` (партия принята, ожидает открытия `signiss1`) или         |
|               | `READY_TO_RECEIVE` (открыт оператором, ждёт прихода пайщика).                |

В пустом состоянии:

> **Нет заказов, ожидающих выдачи на этом кооперативном участке.**

## Жизненный цикл выдачи

Оператор работает в два шага:

1. **Открыть выдачу.** Заказ приходит на ПВЗ в `ACCEPTED_TO_COOP`
   (после приёмки партии, см. [«Приёмка партии»][reception]). Оператор
   подписывает **signiss1** → заказ переходит в `READY_TO_RECEIVE`,
   на пайщика уходит push `marketplace-order-ready` (FR22), карточка
   появляется в [«Готово к получению»][ready] у заказчика.
2. **Закрыть выдачу.** Когда пайщик пришёл на ПВЗ, оператор просит у него
   подтвердить получение. Заказчик подписывает **signiss2** (через свой
   мобильный кабинет, см. [«Получение заказа»][receive]); заказ переходит
   в `RECEIVED`. Backend проводит per-item действия `o.mkt.iss1` +
   `o.mkt.iss2` атомарно.

!!!warning "Без второй подписи имущество не считается выданным"
    Если оператор открыл выдачу (`signiss1`), но пайщик не пришёл —
    заказ остаётся в `READY_TO_RECEIVE` бесконечно. Закрывает заказ
    только финальная подпись заказчика. Это сознательный дизайн:
    юридически выдача имущества от кооператива к пайщику фиксируется
    подписью получателя, а не подписью кладовщика.

## Сайдбар на скриншоте

Слева — обычное меню Стола председателя кооператива. По логике
расширения, при открытии `/market-pvz/*` сайдбар должен переключаться на
набор пунктов оператора ПВЗ (ожидаемые поставки, склад участка, выдача,
гарантийные возвраты), но в текущей сборке остался основной — это
поведение зафиксировано на скриншоте и ожидает доработки workspace-
переключателя.
